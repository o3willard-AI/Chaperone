# Chaperone v0.1.0-alpha.5

**The first release that actually reaches Windows.** `v0.1.0-alpha.3` and
`v0.1.0-alpha.4` were tagged but never published: both runs of the Windows
leg of `release.yml` failed at `cargo build --release --locked` (Unix-only
`std::os::unix` code — the event-feed socket and a policy-guard test helper —
leaking into the Windows compile), which skipped packaging and publish
entirely. `v0.1.0-alpha.2` was the last real release. This tag ships
everything alpha.3 and alpha.4 were supposed to carry, now fixed and
verified end-to-end on real Windows hardware (MSVC toolchain, MSVC-linked
binaries, full workspace test run), plus a Windows-specific reproducibility
fix found during that verification pass.

## Everything from alpha.3 and alpha.4, now actually shipping

Full detail in [v0.1.0-alpha.3.md](v0.1.0-alpha.3.md) and
[v0.1.0-alpha.4.md](v0.1.0-alpha.4.md) — summary:

- **Operator config UI** (`chaperone serve`, default `http://127.0.0.1:8720`):
  setup wizard, secret CRUD, rule editor with mechanism templates, agent
  enrollment, raw TOML editor.
- **Live event feed** (`--events-socket PATH`) and **policy-file integrity
  guard** (D39): load-time permission gate plus a live drift watch that
  halts brokering on any change to a running gateway's `policy.toml`.
- **Per-instance UI access token** (D41): closes the loopback-UI gap where a
  plain TCP listener on 127.0.0.1 has no per-user ACL. `chaperone serve`
  now refuses to start the UI until `chaperone ui-token rotate` has created
  one.

## Fixed: Windows build restored

`crates/gateway-core/src/events.rs`'s `EventHub` and one `policy_guard.rs`
test helper used `std::os::unix` directly, unguarded. Gated both behind
`#[cfg(unix)]` with a `#[cfg(not(unix))]` no-op `EventHub` stub carrying
the same signatures, so the type stays valid and every caller compiles
unchanged on Windows. Audited the rest of the workspace for the same
pattern — console, UDS, audit writer, privileged-helper, UI, CLI were
already gated correctly.

## New: Windows builder brief

[`docs/BUILDER-NOTES-WINDOWS.md`](../BUILDER-NOTES-WINDOWS.md), mirroring

## Changed: no code signing, ever — SLSA reproducible-build posture only

Dropped the ed25519 release-signing path entirely (`release-sign` /
`release-verify` subcommands, the release public key, the `.sig` pipeline
step, the `RELEASE_KEY_SEED` secret). This project is unowned open source
with no entity to hold a signing key. Verification is now exactly two
things, both already true: a **reproducible build** you can reproduce
yourself, and a **SHA-256 hash manifest** (`SHA256SUMS.txt` + per-archive
`.sha256`). Release archives from this tag onward do **not** include
`.sig` files (alpha.1 and alpha.2 did). See
[docs/RELEASE.md](../RELEASE.md).

## Fixed: Windows reproducible builds (D42, new)

The Windows hardware pass that verified the build-restore fix above also
found that two clean `cargo build --release --locked` runs of identical
source produced **different bytes** — 23 bytes, all traced to MSVC
`link.exe`'s default non-deterministic PE `TimeDateStamp` and its derived
debug-directory/PDB-GUID fields. Linux and macOS builds from the same
source have no such field and were already reproducible; this gap is
Windows-only and was silently present in every prior Windows release.

Fixed with `.cargo/config.toml` scoping the `/Brepro` deterministic-linking
flag to `target.x86_64-pc-windows-msvc`. Cargo picks this up automatically
— no `release.yml` change needed. Verified byte-identical across two clean
builds via `scripts/repro-check.sh`. Full writeup: DESIGN-DECISIONS.md D42.

**Honest caveat:** this does not retroactively fix already-published
binaries. `v0.1.0-alpha.1` and `v0.1.0-alpha.2` (the only prior tags whose
Windows leg actually succeeded) predate this flag and are not
independently reproducible by rebuilding today — only the hash-manifest
check (verifying your download wasn't corrupted/swapped) still holds for
those. This is the first tag where the strongest verification path
("rebuild and compare") actually holds on Windows.

## Fixed: install scripts skip the required UI-token step (D41 follow-up)

`chaperone serve` has refused to start the UI without a
`chaperone ui-token rotate`-generated token since D41 landed in alpha.4 —
but alpha.4 never shipped, so this is the first release where the gap is
visible: `install.sh` and `INSTALL.md` never told the operator to run that
command, so the very first service start would fail. Added to the
post-install checklist in `install.sh` and to `INSTALL.md`'s Linux
(systemctl), macOS (launchctl), and Windows (Scheduled Task) sections,
before the service-start step in each.

`cargo test --locked --workspace` on Windows hardware (Rust 1.98.0 MSVC,

build-restore fix above).

## Upgrade from alpha.2

- If you were relying on `.sig` files to verify a download: that path is
  gone. Verify via `sha256sum -c SHA256SUMS.txt`, or rebuild from source
  and compare hashes (`docs/RELEASE.md`).
- Before starting the service (systemd/launchd/Scheduled Task), run:
  ```console
  $ chaperone ui-token rotate --token <path>
  ```
  `serve` will refuse to start the UI otherwise; see `INSTALL.md` for the
  exact command per platform.
- Everything from the alpha.3 upgrade notes (policy.toml must not be
  group/other-writable; editing policy while serving halts the gateway
  until restart) still applies.

Full verification instructions: [docs/RELEASE.md](../RELEASE.md).
