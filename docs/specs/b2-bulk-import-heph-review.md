## Findings to fold in (all code-grounded)

**F1 — `vault set()` is overwrite-by-default.** `local.rs:351` reads *"Stores (or overwrites) the secret at `path`"*. There is no create-only primitive. So "import never overwrites" is not a vault-API guarantee — it's entirely the import command's own `list()` pre-check. Fine, but state it as such, and pin it: acceptance #2 currently asserts `skipped (exists)` + policy byte-identical, but **not** that the pre-existing entry's *value* survived. Seed a known value, import a *different* secret under the same name, assert the stored value is the old one.

**F2 — the policy write is a canonical rewrite and must be atomic.** `Policy::from_toml` drops comments/whitespace; `to_toml()` re-emits canonical TOML (D40's "one writer"). So the first import silently reformats the operator's hand-written policy and **deletes all its comments**. Consistent with the UI's save path, but it's an unstated side effect — name it. Worse, and this is the failure mode you asked me to hunt: the policy file is plain TOML, so a **torn write corrupts the *entire* ruleset** — every rule, not just the imported rows. That's worse than either a dangling row or an unused secret. Require write-temp-then-rename for `--policy`. The sealed vault store has its own integrity; the policy file does not.

**F3 — "D46" and "CA-1" don't exist in the decision registry.** `DESIGN-DECISIONS.md` stops at D44, `SPEC-ISSUES.md` at D14/D8; nothing D45–D49 anywhere; no "CA-1". B-1 forward-ref'd D47 the same way, so it's the same lag — but your spec cites both as recorded rulings. Either register D46 + CA-1 in this PR or point at where the ruling actually lives. Stephen's bar: claims must match the registry.

**F4 — the CA-namespace guard is on `main`; import must reuse it on the resolved path.** `CA_NAMESPACE` (`chaperone/ca/`) and the CLI `refuse_ca_namespace()` guard landed with CA-1 (PR #86, `940b101`), so acceptance #6's dependency is already satisfied — the spec should state that `vault import` routes its entry writes through that same guard rather than re-defining the prefix. The real gap stands: the guard must check the **fully-resolved** entry path (`{scheme}/{name}`), not `name` alone. Your default scheme `local://ssh/fleet` can't hit the CA namespace, but `--cred-scheme local://chaperone/ca` can — test #6's "name would produce `chaperone/ca/...`" is too loose; assert on the resolved path.

**F5 — the CSV source is a plaintext secret store that outlives the run.** The spec says imported secrets never appear in policy/stdout/audit — all true — but the `secrets.csv` file itself holds them in the clear on disk after import. Not a blocker (the operator already had those secrets in plaintext; the import is a strict improvement), but own it: add a post-import warning ("this CSV still contains plaintext secrets; delete or secure it after a successful import") or an optional `--shred-source` flag (shred + unlink after a fully successful run, never on failure).

## Your four questions

**Q1 — TD-3 ordering.** Vault-then-policy is correct. I confirmed the pair rows are an AND-clause evaluated *after* the four shared axes match (`policy/src/lib.rs:485-509`), so a dangling row → `cred_unresolved` denial at request time vs. an unused entry = inert. Ordering is the right cheap atomicity. The worse mode you *didn't* name is **F2** (torn policy write takes down the whole ruleset). Second gap: the **skip-exists → row** semantics are under-specified. On `skipped (exists)`, does import still add the missing pair row? It *must* — that's the only way a phase-1-only crash re-run converges (entries exist → skipped forever → rows never appear). State it in one line and pin it with a crash-recovery test. Related: skip-exists will wire a row to a pre-existing entry that may hold a *different* secret than the operator just fed in — correct (don't overwrite), but the summary should flag it loudly since the row still goes live.

**Q2 — no rule creation.** Right line — an import that can mint rules can mint permissions; keep rule creation human. But it does **not** merely shift toil; it shifts to an *error-prone* toil, because the pair rows are subordinate to the rule's shared axes. A pre-created target rule with `cred_ref = "local://ssh/fleet/*"` but `target_uri = "https://*"` will absorb the imported ssh pairs and **never match them** — the shared `target_uri` filter runs first. Your spec must (a) document the minimal valid import-target rule shape (name + permissive shared axes matching the import's scheme/target), and (b) either validate axis-compatibility on import or warn when the imported `cred_ref`/`target_uri` can't match the rule's own axes. This is your B-1 TD-3-equivalent correction.

**Q3 — pattern blocks.** Agree, skip-with-warning. `Host *.internal` → `HostName %h.internal` is a *template* (the `%h` token), not a host; importing it would fabricate a row naming a pattern. Failing the run would make import unusable on any real ssh_config. One refinement: warn **only** when the pattern block also carries a `HostName` (i.e. would otherwise become a row); a `Host *` settings catch-all (`AddKeysToAgent`, no `HostName`) should be skipped *silently*. And state parser scope explicitly: v1 = flat, no `Include` recursion, no `%h`/`%r` expansion.

**Q4 — acceptance tightening.** Three real ones:
1. **#2** must assert existing-entry *value* preservation (F1), not just "skipped".
2. **Add a crash-recovery test**: pre-seed entries (simulating phase-1-only), run import, assert missing rows *are* added (skip-exists still adds rows).
3. **#8 conflates two failure paths.** `<chaperone:unset>` as a literal string *resolves* (it's non-empty), so it never hits `cred_unresolved` — it'd be brokered and fail at the *target*, and for http-bearer it'd send the literal marker as a real token. "Fails at resolve time" requires a **new vault change**: `resolve()` refuses the sentinel (a `ResolveError::Unset` variant mapped to `E_CRED_UNRESOLVED`). That's real work not in your sizing. My rec: the sentinel-refusal is the honest design (~0.5d), and since ssh-config forces the placeholder path anyway (no secrets), you can't cut it — just scope it. If you'd rather not, fix #8's wording honestly and drop the cred_unresolved claim.
4. *(minor)* #1 should also assert the positive direction (key A *allowed* against host A), plus a negative for the Q2 footgun (restrictive shared axes → imported pair never matches).
